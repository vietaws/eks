# ServiceAccounts

**Learning objective:** understand ServiceAccounts as the identity Pods use to call the API.

"When a Pod talks to the Kubernetes API, who is it? Not you — it's a ServiceAccount. That identity is what RBAC grants permissions to."

## Demo

1. "Imperative first — create a ServiceAccount."
   ```bash
   kubectl create serviceaccount pod-reader-sa
   kubectl get sa pod-reader-sa
   ```
   Expected: the SA exists.

2. "Run a Pod AS that SA; its token is mounted inside."
   ```bash
   kubectl run probe --image=curlimages/curl:8.11.1 --restart=Never \
     --overrides='{"spec":{"serviceAccountName":"pod-reader-sa"}}' -- sleep 3600
   kubectl get pod probe -o jsonpath='{.spec.serviceAccountName}'; echo
   ```
   Expected: `pod-reader-sa`.

3. "The token is mounted at the standard path."
   ```bash
   kubectl exec probe -- ls /var/run/secrets/kubernetes.io/serviceaccount
   ```
   Expected: `ca.crt  namespace  token`.

4. "Clean up."
   ```bash
   kubectl delete pod probe; kubectl delete sa pod-reader-sa
   ```

**✅ Conclusions:**

- Pods authenticate to the API as a ServiceAccount (default if unset).
- The SA token is auto-mounted into the Pod.
- RBAC binds permissions to that SA.
